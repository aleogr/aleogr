# Plugins

One subfolder per plugin. Do not create a plugin's folder before the plugin itself.

Source of truth: [`docs/DESIGN.md` — sections 1, 8, 9, 10 and 12](../../docs/DESIGN.md#1-names).

## Names

- Orchestrator: `aleogr` (skills without provider, e.g. `project-declare`).
- Family plugins: `aleogr-<family>-<provider>` (e.g. `aleogr-repo-github`).
- Family skills: `<provider>_<action>`, given by the **folder name** (e.g. `skills/github_repo-create/`, `skills/aws-route53_record-add/`). Exactly one underscore, between provider and action; hyphens inside each part.
- Object first, action after, in every skill: `repo-create`, `branch-protect`, `project-declare` (the verb may carry a complement: `ci-set-secret`).
- **No `SKILL.md` has `name:` in its frontmatter.** The `description` names the provider.
- Never use built-in command names (`init`, `doctor`, `status`, `review`, `context`, `config`...).

## Family types

- **Exclusive** (one provider per project/domain), **combinable** (several at once); **project**, **component** or **domain** scope. Full map in section 9.
- Each family has a minimum contract of actions, defined in [`docs/CONTRACTS.md`](../../docs/CONTRACTS.md); extra skills follow the same naming convention.
- Every family has a `*-describe` action, and every skill ends with an `aleogr-result` block (CONTRACTS.md section 1).

## Plugin skeleton

```
aleogr-<family>-<provider>/
├── .claude-plugin/plugin.json   ← only the manifest in here
├── skills/<provider>_<action>/SKILL.md
├── bin/aleogr-<family>-<provider> ← the plugin's command, on the Bash tool's PATH
├── agents/                      (optional)
├── hooks/hooks.json             (optional)
├── scripts/                     (optional; reference with ${CLAUDE_PLUGIN_ROOT}); with bin/:
│   ├── aleogr_common.py         ← the shared module, byte for byte the same in every plugin
│   └── skills/<module>.py       ← one per converted skill: the skill's name with - written _
└── .mcp.json                    (optional; official MCP when there is no good CLI)
```

## What exists

- `aleogr` (orchestrator): skills `tools-check` (`gcloud` by default, `gh` with `command=gh`, `go` with `command=go`), `platform-plan` and `platform-apply` (the shared platform, and the login of the organization as the row `login`, prepared as far as a command can), and `project-declare`, `project-plan`, `project-apply`, which write the declaration `.aleogr/project.json` (version 1: the project name, its GitHub repository, its components, its cloud and its environment `dev`) and make the repository match it; `defaults.json`. After the birth a change takes three steps: `project-apply` proposes it as a pull request, the owner merges it, and `project-apply` updates the folder and applies it. A declared component gets its starting point and the project gets its `ci.yml` in that same pull request; after the merge the protection requires the check `ci`. A declared environment `dev` reaches the cloud the same way: the proposal says that applying it creates a GCP project, whose id is permanent, and after the merge one `project-apply` updates the folder and creates its ground (the GCP project, announced before it is made, its APIs, the image repository with its cleanup policy, and the CI identity with push access to it), waiting by itself while APIs it has just enabled still refuse; a declaration without environments runs no `gcloud` command. With components and the environment, once the login is prepared, `project-apply` creates each component's Cloud Run service behind the login and the repository's four CI secrets, then proposes the components' `Dockerfile`s and `ci.yml` with a deploy job for each component whose service exists; the merge deploys. A component declared with `"database": true` (`project-declare component=<name> database=yes`) gets its database check proposed with the declaration, in one pull request whose body says that applying it may start the shared database instance; after the merge one `project-apply` makes the project's database on the shared Cloud SQL instance, the component's database user (its own service account, no password), its two connection roles and its service's three settings, starting the instance first when it is stopped and something must be made in it, only after the check's code is written and a read of the night stop says it is set up, and says so (every plan that may lead to a start says it first); the plan's row `database` never starts it. `project-access` lets one person in to the services (`person=<e-mail>`) or lists who gets in (`list=yes`). Every skill follows the premise of `docs/DESIGN.md` section 10.4: a run goes on by itself, waits are automatic and bounded, one command per thing left to do, short answers.
- `aleogr-cloud-gcp`: skills `gcp_environment-describe`, `gcp_environment-create`, `gcp_services-enable`, `gcp_budget-alert-setup`, `gcp_ci-identity-setup`, the keyless identity of a repository's CI in a project's GCP project (the service account `<project>-ci`, the workload identity pool `github` and its provider `github`, which accept only that repository's default branch; no key, no project role), and `gcp_login-describe` and `gcp_login-setup`, which read and prepare the login of the organization (the IAP setting that names its OAuth client: the setup grants the role and enables the API, and prints the console steps and the one command left to the owner; the client's secret never passes through them). The CI identity's condition also requires a job of the reusable deploy workflow. `gcp_deploy-describe` and `gcp_deploy-setup` read and make each component's Cloud Run service `<project>-<component>` (its own account, the login on from its creation, never public, its login never open to `allUsers` or `allAuthenticatedUsers`, minimum 0 and maximum 2 instances, billing by request, Google's sample image until CI deploys; CI may replace the image, on that service and its account only), and, with `env=`, the settings each service is given (set by name with `--update-env-vars` alone, never with the image; values never in a result block); `gcp_access-grant` lets one person in through the login, or lists who gets in.
- `aleogr-db-gcp-cloud-sql`: skills `gcp-cloud-sql_instance-describe`, `gcp-cloud-sql_instance-create`, `gcp-cloud-sql_instance-start`, `gcp-cloud-sql_instance-stop`, `gcp-cloud-sql_instance-switch-setup` (the shared platform's instance and its night stop), and, for a project's database on it, `gcp-cloud-sql_database-describe` (read-only; a stopped instance is a normal state), `gcp-cloud-sql_database-create` (the database `<project>_<environment>`) and `gcp-cloud-sql_access-grant` (a component's service account as an IAM database user, with no password, then its two connection roles on the shared project). None of these three starts, stops or changes the instance.
- `aleogr-registry-gcp-artifact-registry`: a project's Docker image repository in its own GCP project: skills `gcp-artifact-registry_registry-describe`, `gcp-artifact-registry_repository-create` (the repository `<project>` in the declared region, and the image path), `gcp-artifact-registry_cleanup-configure` (keep the most recent versions of each image, delete the rest, never in dry-run) and `gcp-artifact-registry_access-grant` (push only, on that repository); `files/cleanup-policy.json`, the two rules of the policy.
- `aleogr-repo-github`: skills `github_repo-describe` (which also gives the numeric ids of the repository and of its owner), `github_repo-create`, `github_repo-configure`, `github_branch-protect`, with the `gh` CLI, and, with `gh` and `git`, `github_checkout-setup`, which ties the current folder to the repository, sends the declaration at its birth and brings a folder that is behind up to date after a merge, `github_pull-request-open`, which proposes named files by pull request (a new branch `aleogr/change-<random>`, one open at a time per repository, never merged by the tooling; an optional `note`, up to 300 characters, adds the warnings to its description); and `github_ci-setup`, which writes the project's `.github/workflows/ci.yml` from the declared components (a marker on its first line, one job per component calling `ci-go.yml` of `aleogr/aleogr` pinned by commit, and the job `ci`, plus a deploy job calling `deploy-cloud-run.yml` for each component whose service exists, on push to the default branch only, with the region written in it and the identifiers read from the repository's secrets); `github_variables-set`, the repository's Actions variables, or with `kind=secrets` its Actions secrets (names, never values, in its result); `files/ruleset-main.json`, the ruleset `main` that `github_branch-protect` sends, and `files/ruleset-main-ci.json`, the same plus the required check `ci`, sent with `checks=ci`.
- `aleogr-stack-go`: skill `go_setup`, which writes the starting point of a Go component (`go.mod`, `main.go`, `main_test.go`, from the templates in `files/`) once, only when its folder has no `go.mod` and no Go file, and returns its CI parameters; with `dockerfile=yes` it also writes the component's `Dockerfile` when missing, never overwriting one; with `database=yes` it also writes the component's database check (`db.go`, `db_test.go` and the route `GET /db`, from `files/db.go.tmpl`, `files/db_test.go.tmpl` and `files/main-database.go.tmpl`; `main.go` is replaced only while it is byte for byte the plugin's own) and adds the pinned connector and driver modules with `go get` and `go mod tidy`, the one path that needs Go.
- **Commands.** Every plugin above has one command, `bin/<plugin>` (Python 3, standard library; `<plugin> [--read-only] [--json] <skill> [key=value ...]`), that holds the logic of its converted skills (`docs/DESIGN.md` sections 2.2 and 10.4). Converted in full, and so a shell that runs the command and gives its answer: `tools-check`, `project-plan`, `project-declare`, and every skill of `aleogr-repo-github`, `aleogr-stack-go`, `aleogr-cloud-gcp`, `aleogr-registry-gcp-artifact-registry` and `aleogr-db-gcp-cloud-sql`, both modes. Only the four orchestrators that invoke other skills are prose: `project-apply`, `platform-plan`, `platform-apply` and `project-access`. A command prints each provider command on stderr (`+ ` first) before running it, and the skill's answer and result block on stdout. Its reads go through a runner that refuses any provider command that is not a read; it writes only in `mode=apply`, through a runner that refuses any write its skill does not name. A shell of a skill with `mode` runs `<plugin> --read-only <skill> ...` for every mode but `apply` (the only form its `allowed-tools` names) and `<plugin> <skill> ... mode=apply` for an apply, which Claude Code asks for; `gcp-cloud-sql_instance-start` and `gcp-cloud-sql_instance-stop` have no `mode` and run their one command, which Claude Code asks for. Each Google Cloud refusal of the shared module holds for every skill (no `delete`, no `set-iam-policy`, no primitive role, no public member except in the one removal that closes access, no password, token or key), and a cost gate (`confirm=yes` of `gcp-cloud-sql_instance-create`) is checked in code before the write. A command reaches another plugin only through that plugin's command; when a family's command is not installed, the run fails with one fixed sentence naming the plugin to install.
- Everything else in the design (other families, the other orchestrator skills, hooks) is planned; the tests are in `../tests/` and the declaration's schema in `../schemas/`.
